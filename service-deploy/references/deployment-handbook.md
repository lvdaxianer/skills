# Deployment Handbook Standard

这是一份交给现场实施人员的操作手册标准。手册必须和部署包版本绑定，目标读者是没有 Linux、Docker 或 Kubernetes 经验的人员。

## 1. 手册首页必须写什么

```text
产品：<产品名>
部署包版本：<package_version>
应用版本：<application_version>
构建日期：<build_time>
支持系统/架构：<supported_os>/<architectures>
支持方式：本机直接运行 / Docker / 已有 Kubernetes 集群
预计耗时：<minutes>
权限要求：<root|sudo|namespace-admin>
技术联系人：<name/channel>
```

必须明确：Kubernetes 章节只部署已有集群，不负责创建集群；不在支持矩阵内的系统不得继续安装。

## 2. 一页快速开始

手册最前面必须给出以下入口，命令路径以包根目录为准：

```bash
./doctor.sh       # 只检测，不安装
./deploy.sh       # 首次部署或升级
./service.sh      # 启动、停止、重启、状态、日志菜单
./rollback.sh     # 回滚上一成功发布
./uninstall.sh    # 卸载程序，数据默认保留
```

`service.sh` 至少提供以下选项：

```text
1. 查看服务状态
2. 启动服务
3. 停止服务
4. 重启服务
5. 查看最近日志
6. 查看访问地址
0. 返回
```

每个入口都必须显示包版本、当前 release 或目标身份，并在操作后执行适用的健康检查。手册不得要求实施人员记忆 `systemctl`、`docker compose` 或 `kubectl` 命令。

## 3. 部署前准备清单

```text
[ ] 已拿到完整且有版本的部署包
[ ] 已核对包名、包版本和 SHA-256
[ ] 已确认服务器或集群地址
[ ] 已确认管理员/namespace 权限
[ ] 已确认数据库、缓存、对象存储等依赖
[ ] 已确认访问端口和域名/证书
[ ] 已确认数据备份位置
[ ] 已与客户确认部署根目录、配置、数据、日志和备份目录
[ ] 已逐项确认前端、后端、lib、conf、数据库、MinIO/对象存储和其他不可重建资源的持久化目标
[ ] Docker 已确认绝对宿主机路径；Kubernetes 已确认现有 PVC/PV、Namespace、StorageClass 和绑定状态
[ ] 已指定现场联系人和故障升级联系人
```

## 4. 每一步的固定写法

每个操作步骤 MUST 使用以下结构：

```text
目的：现在要做什么。
操作：只给复制即可执行的命令或一个明确选项。
正常现象：终端应该显示什么。
如果不正常：立即停止、不要猜测，并说明执行哪个诊断入口。
完成标志：如何确认这一步真的完成。
```

示例：

```text
目的：检查当前机器是否满足部署条件。

操作：在命令窗口复制下面一行并按回车：
./doctor.sh

正常现象：所有“必须项”显示“通过”，最后显示“可以安装”。

如果不正常：不要执行 ./deploy.sh，把诊断包路径发给项目联系人。

完成标志：没有必需项显示“不通过”，并且已完成客户目录确认。
```

## 5. 选择部署方式

```text
只有一台物理机/虚拟机，应用直接跑在服务器上：选择“本机直接运行”。
现场已经有正在运行的 Docker：选择“Docker”。
现场已经有人提供可连接的 Kubernetes 集群和命名空间：选择“Kubernetes”。
没有 Kubernetes 集群：不能选择 Kubernetes，安装器会停止。
```

### 本机直接运行章节

必须说明系统、架构、权限、运行时、端口、目录、服务自启动、访问地址、日志、重启、升级和回滚。优先使用包内入口；systemd 细节只作为故障排查信息。

### Docker 章节

必须说明 Docker daemon、Compose/CLI、离线镜像导入或 Registry、端口、持久化挂载、日志、容器恢复、重启、升级和回滚。必须先展示默认资源确认表；前端、后端、lib、conf 使用客户确认的绝对宿主机路径作为可覆盖边界，数据库和 MinIO/对象存储使用独立数据路径。离线部署要明确写“不要执行 docker pull”。

### Kubernetes 章节

必须说明只支持已有集群，如何验证 context、Namespace、权限、镜像、ConfigMap/Secret、PVC/PV、StorageClass、绑定状态、服务暴露和 rollout。前端、后端、lib、conf 的覆盖目录可以为空，空目录使用镜像默认资源；数据库和 MinIO/对象存储必须有独立 PVC/PV 或外部托管证据。检测不到集群、PVC/PV 或绑定状态时必须停止，不使用 hostPath，并给出平台管理员需要提供的清单。

## 6. 配置和客户目录确认

手册必须用表格解释配置：用途、是否必填、示例、默认值、校验规则和安全说明。密码不写入手册、不回显、不进入日志；实施人员不应直接编辑 `.env`、YAML 或 JSON。

安装器必须展示：

```text
程序/release 根目录：<physical path>
配置目录：<physical path>
数据目录：<physical path>
日志目录：<physical path>
备份目录：<physical path>
```

路径必须和客户确认表一致。输入 `CONFIRM-DIRECTORY` 前不得写入或停止现有服务。普通升级不得静默改变部署根目录。

## 6.1 资源持久化确认

在执行任何部署动作前，实施人员必须把以下表格逐项交给客户确认：

| 资源 | 默认状态 | Docker 目标 | Kubernetes 目标 | 是否允许覆盖 |
| --- | --- | --- | --- | --- |
| 前端 | 镜像内有默认值 | 宿主机绝对路径 | 现有 PVC/PV | 是，独立 extension point |
| 后端 | 镜像内有默认值 | 宿主机绝对路径 | 现有 PVC/PV | 是，独立 extension point |
| lib | 镜像内有默认值 | 宿主机绝对路径 | 现有 PVC/PV | 是，不能覆盖镜像 lib 根目录 |
| conf | 镜像可有默认值 | 宿主机绝对路径 | 现有 PVC/PV | 是，外部配置路径 |
| 数据库数据 | 不依赖镜像默认值 | 独立宿主机数据路径 | 独立 PVC/PV | 不适用，必须可恢复 |
| MinIO/对象存储数据 | 不依赖镜像默认值 | 独立宿主机数据路径 | 独立 PVC/PV | 不适用，必须可恢复 |

客户未确认某一行时，只执行 ./doctor.sh 并输出“未完成持久化确认”，不得执行 ./deploy.sh、停止服务、创建容器或创建 Pod。实施人员不手改 YAML/JSON；由入口脚本收集确认并写入部署记录。

## 7. 安装成功验收

```text
[ ] 安装器显示“安装成功”
[ ] 包版本和应用版本正确
[ ] 服务状态正常
[ ] 浏览器/客户端可以访问
[ ] 登录或核心业务操作成功
[ ] 数据可以保存并重新读取
[ ] 服务重启后自动恢复
[ ] 日志目录可以找到
[ ] 数据和备份位置已交接
[ ] 已记录当前 release_id
[ ] 已确认回滚入口可用
```

进程存在、容器为 running、Actuator `UP` 或 Pod 为 Ready 都不能单独作为最终验收。

## 8. 升级、重启、回滚和卸载

- 升级：核对包版本和 SHA-256 → 执行 `./doctor.sh` → 客户目录确认 → 执行 `./deploy.sh` → 按验收单验收。
- 重启：执行 `./service.sh` 选择“重启服务” → 等待状态和健康检查 → 记录输出。
- 回滚：停止继续操作 → 执行 `./rollback.sh` → 等待上一成功版本健康 → 重新执行验收；禁止自行猜 release。
- 卸载：执行 `./uninstall.sh` → 二次确认是否保留数据 → 核对程序、配置、数据、日志和备份处理结果。

如果新版本和记录的 previous release 都无法通过健康检查，必须停止、保留证据并联系负责人，不得选择第三个版本尝试。

## 9. 故障排查和交接

故障章节按现象组织：权限不足、端口占用、磁盘不足、Docker 未启动、镜像导入失败、Kubernetes 不可达、数据库连接失败、健康检查失败、升级失败、回滚失败。每种现象都要写停止条件、`./doctor.sh` 操作、预期输出和联系路径。

交接时提供以下非敏感信息：

```text
部署包版本、应用版本、部署方式、release_id、部署根目录、访问地址、端口、日志目录、备份位置、诊断包路径、部署时间和实施人员。
```

不要提供密码、Token、私钥或完整敏感连接串。
