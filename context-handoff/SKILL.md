# 会话上下文交接

在用户准备切换会话、担心上下文丢失，或明确要求“总结上下文 / 生成交接信息 / 保留重要信息”时使用本 skill。目标不是复述聊天，而是生成新会话可以直接继续工作的事实包。

## 核心规则

1. **只整理当前会话中可追溯的信息。** 用户消息、已经执行的工具输出和已明确确认的结论可以作为事实；计划、猜测、未执行的命令和“也许可以”不能写成已完成事项。
2. **不猜测。** 没有可靠证据的字段写成“未提供”或“待确认”，尤其是服务器、端口、路径、分支、仓库地址、部署方式和命令。
3. **区分状态。** 已确认事实、已完成事项、已确认决策、待确认问题、风险和下一步必须分开，不能把建议写成决定。
4. **保留可操作上下文。** 如果会话中出现，优先保留项目路径、仓库地址、分支、worktree、服务器/环境、端口、部署命令、测试命令、关键文件和失败结果。
5. **先脱敏再输出。** 任何密码、Token、API Key、私钥、Cookie、Authorization 值、带认证的连接字符串或疑似秘密都必须替换为 `[已脱敏]`。不要在输出中复述秘密的原文、前后片段或可逆变形；无法确认是否敏感时也按敏感处理，并提示通过安全渠道补充。
6. **不新增事实。** 不要因为当前工具可以访问某个目录或服务器，就把未在本次交接范围内的实时信息自动加入；只有会话中已有证据或用户明确要求检查时才可加入。
7. **保持复制边界。** 最终回复只输出一个 Markdown 代码块，代码块外不要添加标题、解释、道歉或额外建议。这样用户可以直接点击聊天界面的复制按钮。

## 触发与模式

- 用户说“我要换会话”“帮我保留上下文”“生成交接信息”“总结重要信息”“方便新会话继续”等，直接触发。
- 用户显式调用 `/context-handoff` 时直接触发。
- 默认使用**标准版**：覆盖所有固定字段，但压缩重复描述。
- 用户要求“简洁版”时，只保留目标、项目、当前状态、关键路径/命令、待办、阻塞和下一步；仍然保留安全标记和缺失字段。
- 用户要求“完整版”时，补充决策依据、验证结果、失败尝试、风险、未决问题和证据来源。
- 用户指定字段时，优先满足指定字段，但仍保留安全脱敏、事实标记和“下一步”字段。

## 抽取流程

按以下顺序在内部扫描上下文，完成后只输出交接包：

1. 确定当前任务目标，以及新会话必须知道的背景。
2. 收集项目和环境事实：项目名、用途、本地路径、仓库、分支、worktree、服务器、环境、端口和部署方式。
3. 收集执行状态：已完成、正在进行、失败或回滚的步骤，以及最近一次可靠验证结果。
4. 收集决策和约束：用户明确选择的方案、不能违反的限制、接口/数据/兼容性要求。
5. 收集行动项：按优先级列出下一步、阻塞项、待确认问题和风险。
6. 对每一项标注状态：`已确认`、`待确认`、`未提供` 或 `推断（不要当作事实）`。能避免推断时优先不写推断。
7. 做一次敏感信息扫描，再渲染最终 Markdown。扫描到秘密时只保留字段用途，不保留原值。
8. 检查输出：所有已完成事项都有会话证据；未提供的运行信息没有被补全；没有输出任何秘密；只存在一个代码块。

## 质量与安全检查

输出前逐项检查：

- 是否只有一个 Markdown 代码块？
- 是否包含用户请求的字段，以及标准字段中的目标、状态、待办和下一步？
- 是否把计划误写成完成，把建议误写成决策，或把推断误写成事实？
- 是否明确标出服务器、路径、分支、端口等缺失信息？
- 是否脱敏了所有密码、Token、私钥、Cookie、认证 URL 和疑似秘密？
- 是否保留了失败结果、风险和未决方案，而不是只留下“进展顺利”？
- 新会话是否能仅凭这份交接包判断接下来做什么？
