# 开发型产品实现工作流参考

本流程吸收 `development-workflow` 的有效机制，但不要求每个项目都执行完整的 OpenSpec、分支 Worktree、子 Agent 编排和逐任务合并流程。

## 阶段与门禁

### 1. 输入分析

识别输入是文字需求、设计图，还是二者同时提供；检查已有项目、可复用组件、启动命令、测试命令和现有 API。不要把设计图中看不见的业务行为当成事实。

### 2. Brainstorming

强制使用 `superpowers:brainstorming`：

1. 先读取项目上下文。
2. 一次只问一个关键问题。
3. 优先澄清会改变页面范围、数据边界、权限或验收结果的问题。
4. 提出交互和实现范围，不重新选择固定技术栈。
5. 形成设计结论、假设和验收标准。
6. 等待用户确认设计后再进入实现。

设计未确认时，允许读文件和讨论，不得创建实现代码、迁移、组件或测试实现。

### 3. 设计映射

形成页面/路由清单、组件树、状态矩阵、业务模块、用例、API 草案、错误码、Repository 边界和测试场景。把设计图中未表达的状态补齐，并区分“已确认”和“推断”。

### 4. 任务拆分

每个任务必须有清晰边界：负责模块、允许文件、排除范围、依赖、聚焦验证命令、 broader verification 命令和交接证据。任务必须小到可以独立执行 RED/GREEN/REFACTOR。

### 5. TDD

每个行为任务执行：

```text
RED       写最小失败测试，运行并确认失败原因
GREEN     写最小生产代码，运行并确认通过
REFACTOR  消除重复、整理依赖和命名，保持测试通过
VERIFY    执行更大范围测试、lint、build 或用户流程检查
```

测试必须表达用户或业务行为。测试先通过，或失败原因是语法/测试自身错误时，不能进入 GREEN。

### 6. 专项实现

- 前端加载 `frontend-interaction-guidelines`，必要时再加载 Vue 相关 Skill。
- 后端加载 `backend-reliability-guidelines`。
- 生产日志加载 `logging-boundaries`。
- 所有代码加载 `code-review-spec`。
- 新增对外路由加载 `rest-api-documentation`。
- 新增构建清单、工具目录、环境变量或基线文件时加载 `project-hygiene`。

具体 Skill 的规则高于本参考资料；本资料只负责编排时机。

### 7. 审查与验证

先检查实现是否符合设计映射和任务范围，再按领域 Skill 审查。修复发现后重新运行聚焦测试和 broader verification。必须有新鲜命令输出才能声称通过。

### 8. 交付

交付说明必须包含启动、测试、构建命令，已实现范围，假设，未实现事项，API 文档位置和可复用边界。任何必需验证失败都要明确报告，不得用“应该可以”替代证据。

## 变更类型处理

- 新项目：按固定布局生成最小可运行前后端。
- 已有项目：先复用已有边界和组件，只有在缺失能力时才新增；不得为了套模板大范围重写。
- 纯视觉调整：仍需验证交互没有回归；若不改变行为，可用组件/视觉检查代替新增行为测试，但必须说明原因。
- 业务行为调整：必须执行完整 TDD。
