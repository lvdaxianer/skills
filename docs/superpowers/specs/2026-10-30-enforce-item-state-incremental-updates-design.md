# 列表项独立状态增量更新设计

## Context

现有前端交互规范只要求进度等中间状态按稳定数据 ID 增量更新，未覆盖启用、停止、发布、归档及已有项字段更新。此次设计用于补齐该行为边界，并与 OpenSpec change `enforce-item-state-incremental-updates` 保持一致。

## Goals / Non-Goals

**Goals:**

- 要求已有列表项的独立状态或字段更新只合并到受影响的稳定 ID。
- 在主 skill 与 checklist 中使用一致的规则、示例和例外。
- 明确新增、删除与筛选/排序/分页结构校正的边界。

**Non-Goals:**

- 不规定具体状态管理库、缓存实现或 API 返回格式。
- 不改变新增、删除等列表结构变化的既有处理方式。

## Decisions

### 使用稳定 ID 作为局部更新边界

单项和批量状态更新都按响应中的稳定 ID 合并受影响字段，避免通过整页替换来反映局部变化。规则覆盖启用/停用、启动/停止、暂停/恢复、发布/下线、归档/恢复、审批/拒绝、置顶/取消置顶、已读/未读和普通字段编辑。

### 仅在结构条件变化时校正列表

成功的局部更新默认保留分页、排序、筛选、选择和交互上下文。如果状态变化使项离开当前筛选、改变排序位置或改变分页归属，才允许在局部更新成功后重新查询列表校正结构。

### 保持规范与审核清单同步

`SKILL.md` 作为实现与 Review 的强制规则，`interaction-checklist.md` 作为审核检查项；两者采用同一边界语言，OpenSpec delta 则以场景固定成功、批量、失败/过期和结构校正行为。

## Risks / Trade-offs

- 局部更新可能改变当前查询结构，因此结构校正必须是成功后的条件路径，而非默认刷新。
- 批量操作可能部分成功，因此必须按成功响应中的 ID 更新，并为失败项保留恢复反馈。

## Migration Plan

这是规范文档变更，不需要运行时迁移。提交后归档 OpenSpec change，使新增 requirement 合并到 `frontend-interaction-reliability` 主 spec；若规则需要回退，可回滚文档提交。
