# 异步操作反馈设计

## 背景

前端交互规范已经覆盖 loading、禁用、防重复、失败恢复和乐观更新，但没有统一规定异步操作从用户触发到请求终态的反馈生命周期。典型问题是用户在删除确认框中点击确认后，弹框立即消失，删除请求仍在进行，却没有任何处理中反馈，用户无法判断操作是否生效。

## 设计目标

- 所有状态变更操作在触发后立即进入可识别的 pending/busy 状态。
- 删除、保存、提交、发布、支付、上传、导入和批量操作使用一致的成功、失败、取消和长任务反馈。
- 请求未完成时默认保持弹框、抽屉或表单可见；如果业务必须关闭，受影响内容仍保留可找回的处理中状态。
- 只有成功终态才关闭、跳转、清空或移除；失败、超时、离线和取消必须停止 loading 并提供恢复路径。
- 规则同时出现在 skill 强制条款和交互 checklist，且安装副本与仓库源一致。

## 方案

新增“异步操作生命周期与反馈”规范层，定义 `pending`、`success`、`error`、`cancelled` 和 `long-running/background` 状态。删除场景作为高风险操作示例，明确确认按钮持续 loading 直到删除请求成功或失败；通用规则则覆盖保存、发布、支付、上传、导入和批量操作。

短请求沿用现有约定：控件立即禁用以防重复，但可以省略短暂 spinner 以避免闪烁。中长请求使用局部 loading、进度或后台任务状态，不默认阻塞整页。失败时保留必要输入与上下文，并提供 retry、undo、cancel 或其他适用恢复路径；旧响应不能覆盖更新后的状态。

## 验证

使用 OpenSpec 严格校验、关键词和 Markdown 结构检查、仓库源与安装副本 `cmp`、现有 baseline 测试及全 diff 审查，确保五类异步生命周期要求在规范与 checklist 中均可追踪。

## 非目标

不修改业务前端代码、后端 API、组件库或依赖，不规定具体框架、请求库、错误码、进度协议和后台任务存储方式。
