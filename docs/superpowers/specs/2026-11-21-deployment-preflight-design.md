# 一键部署前置检查设计

## 背景

现有 `service-deployment` skill 已经要求检查端口、目录、空间和权限，但这些要求分散在多个参考文件中，部署包 manifest 没有统一表达方式，导致“包构建通过”与“目标机可以安全部署”之间存在断层。本设计把检查分为构包静态检查、目标机只读检查和部署强制门禁三层。

## 方案

manifest 新增 `preflight` 契约，至少声明：

- 所支持模式的通用检查和模式专属检查；
- 端口协议、监听边界、端口号和允许的冲突身份；
- 目标路径的最小可用字节、inode 和安全余量；
- 运行用户需要的 owner/group、文件模式和读写执行能力；
- 资源、依赖、配置、持久化、生命周期、日志和回滚空间检查要求。

`package-contract-test.sh` 只验证这些声明完整且格式安全。`doctor.sh` 根据客户确认的物理路径和运行身份执行只读检查，生成绑定 package SHA、部署模式、路径和时间的脱敏报告。`deploy.sh` 在停止、写入、创建容器/Pod 或切换 `current` 前验证报告，任一必需项失败都保持 dry-run。

### 失败边界

端口被不明进程占用、可用空间或 inode 低于预留、owner/group 或权限不满足、现有服务身份无法唯一证明、依赖或持久化目标不可用时，直接失败。升级时只有当端口属于记录的 current release 或精确容器/workload identity 才能通过冲突检查。

一键入口不自动杀进程、改端口、清理磁盘、修复权限、修改防火墙或安装 Docker/Kubernetes。现场必须按诊断建议由管理员处理后重新运行 doctor。

## 验证

- 缺失 preflight、无效阈值、未知检查和不安全路径的清单被契约测试拒绝。
- 完整清单通过既有 package/persistence 合约测试。
- 文档和 skill 明确三层顺序及所有部署模式的停止条件。
- OpenSpec strict validation、shellcheck 可用时的 shell 语法检查和全部 service-deploy 测试通过。

## 不在范围内

本次不实现具体客户环境的端口探测器或自动修复器，不执行真实部署，不改生命周期状态机，不安装外部运行时。
