# Knowledge Notes

## Purpose

把项目里的 Markdown/文本笔记当作一个可导航的知识系统来维护：先定位节点，再写内容、建关系、做对比，必要时补充配图或可编辑架构图。

## Scope

- 适用于新写、改写、整库治理、链接维护、相近主题整理和笔记配图。
- 默认直接修改项目文件；完成后报告变更，不停在“建议修改”阶段。
- 不绑定 Obsidian、固定目录或 frontmatter。先复用项目已有的命名、目录、索引、链接和资源约定。
- 用户只要求分析或审阅时，不修改文件。
- 不为增加链接数量而互链；不在证据不足时删除、合并或重命名笔记。

## Workflow

### 1. 预检项目知识库

先读取项目内相关 Markdown/文本文件和入口页：

1. 使用 `rg --files` 定位 `.md`、`.markdown`、`.txt` 及现有资源，排除 `.git`、依赖、构建产物和工具缓存。
2. 找到主题索引、README、目录页、术语表和目标笔记的前后相邻内容。
3. 识别笔记角色、主题层级、已有关系、断链、孤立节点和同类主题。
4. 记录项目已有的资源目录、图片引用和图表格式。没有约定时只建立最小必要结构。

### 2. 选择工作模式

- **新写/改写**：先定义笔记要回答的问题、知识角色、前置知识、后续知识、相邻概念和边界，再写正文。
- **治理/修复**：扫描孤立笔记、断链、失效图片、重复内容、索引不一致和术语漂移，直接修复确定问题。
- **关系/对比**：围绕同一组差异维度整理相近主题，补充选择依据和双向导航。
- **视觉表达**：仅在图形能降低理解成本时配图；架构主题优先使用可编辑 Mermaid/文本图。需要细则时读取 [references/visualization.md](references/visualization.md)。

### 3. 写出故事线

围绕一个可回答的问题推进，而不是堆概念。默认顺序是：

`背景/问题 → 核心概念 → 运作机制 → 示例或证据 → 边界/限制 → 相近主题对比 → 应用/下一步`

根据笔记角色调整顺序：索引强调导航，决策记录强调约束和取舍，方法笔记强调前提、步骤和验证。每一段都要说明它为什么接在上一段之后。

### 4. 建立有语义的关系

用项目既有格式，或用带上下文的 Markdown 链接表达关系。优先使用这些关系：上位/下位、前置/后续、相近/对立、方法/示例、原因/结果、替代方案/场景。链接到相邻笔记后，在不会造成噪声时补充反向入口或索引项。关系选择和治理矩阵见 [references/knowledge-model.md](references/knowledge-model.md)。

### 5. 强制差异化

对相近主题至少比较与当前问题相关的维度：解决的问题、抽象层级、前提、适用场景、代价、限制和输出。明确“何时选 A、何时选 B、为什么”，不要用“都很重要”代替边界。高度重叠时评估合并或重新划分；不确定时保留信息并报告。

### 6. 维护视觉资源

- 概念图、流程图或场景图只有在比文字更能建立直觉时才生成，并写入项目约定的资源目录。
- 架构图必须表达组件职责、边界、方向、数据流/时序和关键约束；优先保留 Mermaid/文本图源，SVG/PNG 只是派生展示物。
- 使用图像生成工具时，提示词必须来自笔记事实和视觉目的；不可把不确定架构事实交给图片臆造。
- 图片、图表和正文必须互相可追溯：相对路径有效、替代文本描述用途、图中元素能在正文找到说明。

### 7. 直接修改和收尾

直接写入新笔记、相关索引、相邻笔记和确定的资源引用。完成后检查链接和资源路径，并报告：

- 修改、新增或删除了哪些文件（删除仅限用户明确要求或已确认安全）。
- 每个改动解决了什么体系问题。
- 新增了哪些关系、对比、图表或图片。
- 哪些合并、删除、命名或事实冲突因不确定而保留。
