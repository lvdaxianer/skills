# Design

## Context

当前技能已覆盖列表、加载、实时状态和运行时性能，但没有把分页查询与中间状态更新的请求边界写成强制规则。详见 `proposal.md` 的动机与范围。

## Goals / Non-Goals

**Goals:**

- 在技能红线和检查清单中形成同一套可审查的分页与增量更新要求。
- 明确列表数据与中间状态的分离：列表负责分页数据，状态请求负责按稳定 ID 更新状态字段。
- 保留分页位置、排序和用户交互状态，避免状态刷新导致整页重建。

**Non-Goals:**

- 不规定具体分页协议（页码、游标或分页字段命名）。
- 不规定轮询、SSE 或 WebSocket 的具体实现，也不修改后端接口契约。
- 不规定通用状态刷新频率；具体频率由业务场景和服务端能力决定。

## Decisions

- **在技能红线与参考清单双写规则。** 技能文件负责强制约束，参考清单负责审查落点；两处使用一致的行为定义，避免只更新一侧造成执行偏差。
- **将状态请求限定为稳定 ID 的单独请求。** 相比重复拉取整页列表，这样能降低网络和渲染成本，并使状态更新与列表数据生命周期解耦。
- **采用按 ID 的合并更新。** 相比替换整个分页结果，按 ID 更新可保留排序、分页位置、选择和焦点等用户上下文；状态更新失败时只影响对应状态反馈。
- **不绑定具体传输技术。** 轮询、SSE 和 WebSocket 都可以满足“按 ID、增量更新”的行为契约，避免规范过早锁定实现。

## Risks / Trade-offs

- [Risk] 列表 API 缺少稳定 ID → [Mitigation] 将“列表结果必须提供稳定数据 ID”作为中间状态场景的硬性前置条件，并在无法满足时阻止实现进入无边界状态刷新。
- [Risk] 页面切换或筛选后旧状态响应回写 → [Mitigation] 结合当前分页 ID 集合和请求生命周期，取消或忽略已离开当前页的状态响应。
- [Risk] 不同业务对“增量”理解不一致 → [Mitigation] 在规范中明确增量更新是只合并发生变化的 ID 对应状态，不替换整页列表。
