# Design

## Context

本 change 只更新前端交互规范及其安装副本，不修改业务组件或请求实现。当前 `frontend-interaction-guidelines` 已分别描述 loading、禁用、防重复、乐观更新、失败恢复和长任务，但这些条款没有形成统一的请求生命周期，也没有明确确认弹框在请求未结束时的行为。具体行为契约见 `specs/frontend-interaction-reliability/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在 skill 红线、implementation mode 和交互 checklist 中使用一致的 pending → terminal 状态模型。
- 让删除确认、保存、提交、发布、支付、上传、导入和批量操作都能审查“触发后如何反馈、何时结束、失败如何恢复”。
- 保留现有约定：短请求避免 spinner 闪烁，破坏性操作需要确认，乐观更新必须回滚或提供恢复。
- 保证仓库 canonical 文件与当前安装副本保持字节一致。

**Non-Goals:**

- 不引入前端状态机库、组件库或请求库。
- 不规定具体 API、错误码、进度协议、轮询频率或后台任务存储方案。
- 不修改业务代码，不为每个业务操作设计单独的文案或视觉样式。

## Decisions

- **用统一生命周期规则覆盖操作类型。** 在 skill 中定义 `pending`、成功、失败、取消和长任务状态，再用删除等高风险操作说明默认行为。相比只新增“删除按钮 loading”，这种方式可复用于保存、发布、支付、上传和批量操作，减少跨页面漂移。
- **默认保持发起操作的承载面可见。** 对话框、抽屉和表单在请求未结束前保持打开，确认按钮显示 loading 并禁止重复触发；如果业务必须关闭，则必须在受影响内容处留下可找回的处理中状态。相比立即关闭，这能保留用户对当前请求的上下文和结果预期。
- **用终态驱动数据变更。** 成功响应到达后才关闭、跳转、清空或移除数据；失败、超时、取消和离线恢复为可操作状态并保留输入。相比依赖固定延时或 toast 推断完成，终态驱动能避免慢网络下的错误反馈。
- **在两个规范层级同步表达。** `SKILL.md` 负责强制红线和实现时的状态定义，`interaction-checklist.md` 负责审查时的逐项验证；两者使用同一术语和示例，安装副本完整镜像仓库源。
- **保留现有等待阈值和局部反馈原则。** 控件应立即进入 busy/disabled，但极短请求可以不显示 spinner；中长请求使用局部 loading、进度或后台任务状态，不默认阻塞整页。

## Risks / Trade-offs

- [Risk] 规则被误解为所有操作都必须阻塞式保持弹框 → [Mitigation] 明确“默认保持可见”，同时允许有记录的后台任务例外，但要求受影响内容保留 pending 状态和防重复能力。
- [Risk] 同一条规则与现有乐观更新、undo 规则产生冲突 → [Mitigation] 保留可逆低成本操作优先 undo 的现有原则；异步生命周期只规定反馈和终态，不取消合适的乐观更新，但要求失败回滚或恢复。
- [Risk] 安装副本手工同步后再次漂移 → [Mitigation] 在任务验收中对两个 `SKILL.md` 和两个 checklist 执行 `cmp`，并把同步作为独立任务步骤。
- [Risk] 文档规则覆盖范围过大、难以审查 → [Mitigation] 每条规则绑定可观察场景，按短请求、局部操作、长任务和无障碍反馈拆分 checklist 条目。
