# Design

## Context

本次变更只更新技能规范。现有后端规则已经要求批量操作定义事务、幂等和恢复行为，日志规则也禁止循环内逐条输出；本设计补充导入解析与数据库写入之间的缓冲窗口、批量阈值和失败恢复边界。

## Goals / Non-Goals

**Goals:**

- 明确导入链路必须经过解析、校验、缓冲/排队、批量提交，而不是逐条写库。
- 明确批处理窗口与 batch size 的触发关系，避免用无界缓存或阻塞式 sleep 实现“延迟”。
- 明确批次事务、幂等、部分失败、重试、断点恢复和背压要求。
- 明确日志按批次汇总，能够用 traceId 和 batchId 关联排障。

**Non-Goals:**

- 不选择具体消息队列、数据库驱动、ORM 或调度框架。
- 不规定所有导入都必须异步；小型同步导入仍须遵守有界批处理和事务规则。
- 不修改具体项目的导入接口、表结构、依赖或运行时参数。

## Decisions

1. **把“延迟”定义为可配置的批处理窗口。**
   解析结果进入有界 buffer、queue 或 staging 后，在窗口内收集记录；窗口到期或达到 batch size 阈值时，以先满足者触发批量提交。相比固定 `sleep`，这种方式能合并写入、避免阻塞请求线程并在高流量时提供背压。

2. **批量大小、窗口时长和缓冲容量必须有上限。**
   任何一个参数未配置或超出数据库/消息系统安全边界时，系统应拒绝启动或使用经过审查的安全默认值；禁止无界内存积压和一次性全量提交。

3. **每批使用独立、可重试的事务边界。**
   单批成功后提交并记录进度；失败批次保留输入范围和错误原因，按幂等策略重试或进入失败记录/死信路径。一个批次失败不应静默丢失其他批次，也不能在未确认成功时标记导入完成。

4. **导入必须具备幂等和重复检测。**
   使用导入任务 ID、业务唯一键或去重记录防止请求重试、任务恢复和消息重复投递造成重复写入。前端禁用或延迟不能替代后端幂等。

5. **日志按批次汇总并保留可追踪上下文。**
   每个批次使用 traceId 和 batchId 关联，记录总数、成功数、失败数、耗时和有限失败样本；禁止在解析或入库循环内逐条打 INFO/ERROR。

## Risks / Trade-offs

- [窗口增加单条数据延迟] → 窗口必须可配置，并在达到 batch size 时提前提交；长任务显示排队/处理状态。
- [批次失败导致部分完成] → 持久化批次状态、失败明细和重试次数，提供断点恢复或死信处理。
- [批量过大造成数据库压力] → 限制 batch size、连接和事务耗时，按数据库参数和压测结果配置。
- [缓冲积压造成内存增长] → 使用有界队列、背压、拒绝/暂停策略和积压指标，不允许无限缓存。

## Migration Plan

无需迁移运行时数据。后续导入功能改造时，先补充批次状态、幂等键和失败恢复测试，再逐步把逐条写入切换为窗口/阈值触发的批量写入；如出现异常，可按批次回退到受控重试或暂停消费，不恢复为无界逐条写入。
