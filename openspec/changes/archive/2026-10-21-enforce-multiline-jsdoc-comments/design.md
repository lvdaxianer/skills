# Design

## Context

`development-workflow` 负责把代码注释要求委托给 `code-review-spec`。现有规范和示例描述了完整标签，但没有统一的、可审查的换行契约；因此生成结果可能在语义正确的同时被压缩为单行。详细行为要求见 `specs/multiline-code-comments/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在代码审查规范的规则层明确多行 JSDoc 的硬性格式。
- 在审查清单中增加可直接判定的单行注释失败项。
- 让 TypeScript/Vue 模板与强制规则保持一致。

**Non-Goals:**

- 不修改业务代码、运行时行为或格式化工具配置。
- 不强制所有语言使用 JSDoc；各语言仍遵循其惯用文档注释语法。
- 不要求对历史代码进行全量重排，本次规则面向生成、修改和审查的代码。

## Decisions

1. **在 `code-review-spec` 主规范中增加硬性排版规则。**
   - 选择原因：该 skill 是代码注释格式的权威入口，能够同时约束生成和审查。
   - 备选方案：只修改示例。未采用，因为示例容易被当作参考而不是失败条件。

2. **将单行 JSDoc 加入审查清单的强制项。**
   - 选择原因：主规则定义要求，清单提供可执行的验收证据，避免只写规则但审查时遗漏。
   - 备选方案：只依赖模型遵循自然语言要求。未采用，因为缺少明确的失败判定。

3. **保留现有多行模板，并补充禁止单行的反例说明。**
   - 选择原因：生成器需要正向模板，审查者需要明确的反向边界。
   - 备选方案：删除模板，仅保留抽象规则。未采用，因为跨语言注释语法仍需要示例。

## Risks / Trade-offs

- [旧代码存在单行 JSDoc] → 规则针对新增和修改内容；审查旧代码时按变更范围处理，避免无关的大规模格式化。
- [不同语言的注释语法不同] → 仅对 JSDoc 规定 `/**`、`*/` 和标签独占行，其他语言保留语言惯例。

## Migration Plan

1. 更新 `code-review-spec/SKILL.md`、`spec.md` 和注释模板/清单。
2. 使用文本检索与 OpenSpec 校验确认规则和示例一致。
3. 合并后，后续代码生成和审查按新规则拒绝单行 JSDoc；无需数据迁移或回滚脚本。
