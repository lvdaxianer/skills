# Design

## Context

本次变更只更新后端可靠性与日志边界技能。现有规范已经要求错误响应稳定、内部异常不外泄、业务日志带 traceId、异常保留 stack，以及异步上下文透传；本设计将这些分散约束收敛为一条可执行的“用户错误契约 + 内部诊断上下文”规则。

## Goals / Non-Goals

**Goals:**

- 明确机器可处理的错误类型/错误码与稳定中文消息之间的映射。
- 明确全局异常处理器的响应边界、日志边界和 traceId 一致性。
- 明确 ThreadLocal/MDC 及异步线程上下文的设置、透传和清理要求。
- 让后续实现可以用契约测试验证错误响应、日志和线程复用安全。

**Non-Goals:**

- 不选择具体 Web 框架、日志框架或 trace 平台。
- 不规定所有项目必须使用 Java ThreadLocal；非 Java 项目使用等价的请求上下文机制。
- 不修改现有业务 API、异常类、依赖或部署配置。

## Decisions

1. **以 `errorCode + message + traceId` 作为最小公共错误响应。**
   `errorCode` 供前端和其他调用方稳定分支，`message` 使用明确中文，`traceId` 用于客服和运维定位。相比直接返回异常类名或 HTTP server 文本，这个契约不会把框架实现暴露为公共行为。

2. **用错误类型枚举驱动全局异常映射。**
   至少区分参数校验、认证、授权、资源不存在、冲突/幂等、限流、上游失败和未知内部错误；每类绑定 HTTP 状态、稳定错误码和中文默认消息。相比在各 Controller 临时拼接消息，枚举集中维护更容易兼容和审查。

3. **原始异常只进入脱敏日志，不进入公共响应。**
   全局处理器在单一边界记录原始 throwable/stack 与安全上下文，响应只返回安全字段；密码、token、密钥、完整个人信息和原始请求值必须脱敏或省略。相比把 `getMessage()` 直接返回前端，这能避免内部实现和敏感数据泄露。

4. **请求上下文由入口统一建立并在 finally 清理。**
   traceId 可在可信格式校验后透传，否则生成新值；写入 MDC/ThreadLocal 兼容上下文，并由日志框架自动输出。异步任务必须显式快照并恢复上下文，执行完成后清理，防止线程池复用串号。

5. **`code-review-spec` 只作为实现审查门禁。**
   业务错误契约属于后端可靠性，日志字段和脱敏属于 logging-boundaries；不把运行时规则写进代码审查标准，避免职责混淆。

## Risks / Trade-offs

- [错误码变更影响调用方] → 要求错误码稳定、中文文案可迭代但不改变语义，并通过契约测试保护。
- [ThreadLocal/MDC 在线程池中串号] → 强制入口 finally 清理、任务级快照恢复和异步透传测试。
- [记录原始异常造成敏感信息泄露] → 统一脱敏后再记录，禁止原始请求 body、凭据和个人敏感字段进入任何级别日志。
- [多层重复记录同一异常] → 明确由全局处理边界统一记录，底层包装异常时不重复打 ERROR。

## Migration Plan

无需迁移运行时数据。技能文件合并后，后续后端改动按新规则实现；若项目已有错误响应契约，应先建立兼容映射和契约测试，再逐步替换框架默认错误文本。
