# Design

## Context

现有 `frontend-interaction-guidelines` 已要求进度等中间状态按稳定数据 ID 合并更新，但主 skill 与 checklist 尚未把该模式推广到已有列表项的启用、停止、发布或字段更新。参见 `proposal.md` 与 delta spec，本次变更只涉及规范文本、审核检查项和 OpenSpec 行为契约。

## Goals / Non-Goals

**Goals:**

- 在主 skill 中建立适用于所有已有列表项独立状态或字段更新的增量更新规则。
- 在 checklist 的数据变化和操作可靠性维度中提供可执行的审核检查项。
- 明确新增、删除和因筛选/分页/排序变化产生的结构校正之间的边界。
- 保持与现有分页、异步生命周期、乐观更新和过期响应规则一致。

**Non-Goals:**

- 不设计具体 store、query cache、状态管理库或 API 返回格式。
- 不要求新增和删除也采用局部字段更新。
- 不改变现有业务代码或运行时行为。

## Decisions

### 以稳定 ID 作为增量合并边界

主 skill 和 checklist 都使用“稳定数据 ID + 仅更新受影响字段”的表述。这样既覆盖单项更新也覆盖批量更新，同时避免把整个实体对象作为组件或列表刷新载体。替代方案是只要求“局部刷新”，但该说法无法验证是否错误地替换了整页数据。

### 将结构校正定义为成功后的例外路径

默认路径必须保留列表上下文；只有状态变化确实使项离开当前筛选、改变排序位置或改变分页归属时，才允许重新获取列表校正结构。替代方案是禁止所有刷新，会导致界面继续展示不符合当前查询条件的项。

### 在规范和 checklist 中使用相同的边界语言

主 skill 面向实现和 Review 的强制规则，checklist 面向逐项审查，因此两者共享同一组例子和例外。OpenSpec delta 另以场景形式固化成功、批量、失败/过期和结构校正行为，避免只检查文字存在而没有行为证据。

## Risks / Trade-offs

- [风险] 局部更新后列表排序或筛选条件已不再成立 → 仅在成功响应确认结构条件变化时触发列表校正，并保留局部更新作为默认路径。
- [风险] 批量操作的部分成功被误处理为整批成功 → 要求按成功响应中的受影响 ID 更新，失败项保留恢复反馈。
- [风险] 主 skill 与 checklist 未来再次产生措辞漂移 → 本次同步修改并在验证阶段执行关键术语和边界检查。

## Migration Plan

1. 更新主 skill、checklist 和 OpenSpec delta。
2. 使用严格 OpenSpec 校验与文档一致性检查验证规则和场景。
3. 归档 change 时由 OpenSpec 将 delta 合并到现有 `frontend-interaction-reliability` 主 spec。
4. 若发现规范过严，可回滚本次文档提交；不涉及运行时迁移或 API 回滚。
