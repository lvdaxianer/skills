# Design

## Context

本次变更只调整前端交互技能的规范文本，不修改项目运行时实现。现有技能已经要求列表按稳定 ID 增量更新、保护过期响应，并区分局部加载与整页加载；本设计补充这些规则在刷新/轮询场景下的具体防闪烁约束。

## Goals / Non-Goals

**Goals:**

- 在同一处技能规则中明确刷新期间保留列表 DOM 挂载。
- 明确首次加载与已有数据刷新使用不同的反馈策略。
- 将稳定 row key、逐行浅比较、对象引用复用和慢网络 DOM 验证写成可执行验收要求。

**Non-Goals:**

- 不修改应用组件、状态管理、接口或测试代码。
- 不规定具体框架组件库、请求库或视觉样式。
- 不新增项目 OpenSpec 运行时能力，因此跳过 capability spec。

## Decisions

1. **在 Non-Negotiable Interaction Rules 中新增专门小节。**
   这能让防闪烁要求与现有列表分页、按 ID 增量更新、过期响应规则处于同一强制级别。将其放入 checklist 或单独文档会降低实现时的可见性。

2. **用“数据存在性”而不是 `loading` 控制列表显示。**
   首次无数据时允许阻塞式占位；已有数据刷新时保留旧内容，只在触发刷新按钮上反馈 busy。相比刷新时替换整表的全屏 loading，这能保持用户上下文和 DOM 实例稳定。

3. **用稳定 ID 的行级合并作为刷新路径要求。**
   全量响应仍可用于获取最新数据，但合并时逐行浅比较并复用未变化行引用；只有结构变化或真实字段变化才更新对应部分。相比直接替换数组，这能限制重绘范围。

4. **把手动刷新、自动轮询和慢网验证一起写入规则。**
   只约束手动刷新会遗漏轮询路径；只写实现建议又难以验收，因此三者必须在同一规则中出现。

## Risks / Trade-offs

- [规则与现有增量更新要求重复] → 使用交叉一致的术语并限定本节只处理刷新挂载、行级复用和验证方式。
- [文档规则过度绑定某个框架] → 仅以 `v-if` 作为常见反模式示例，核心要求使用框架无关的“保持挂载”和“稳定 ID”表述。
- [文档变更无法运行真实浏览器验证] → 将约 1 秒网络延迟下的 DOM 节点身份断言写成后续实现的验收要求，本次通过内容检查和 OpenSpec 校验确认规则完整。

## Migration Plan

无需迁移或回滚运行时数据。提交技能文档后，后续前端实现和 review 按新增规则执行；若规则措辞需要调整，可通过单独文档变更回滚该段内容。
