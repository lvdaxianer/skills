# Design

## Context

参见 `proposal.md` 的动机与范围。现有日志 skill 已要求业务上下文携带 `traceId`，但定时任务场景同时要求固定开始/结束日志，造成“链路可查”和“日志降噪”之间的冲突。现有仓库是跨语言日志治理文档集合，本次不引入运行时实现，只补齐可落地的规范、示例和 review 检查点。

## Goals / Non-Goals

**Goals:**

- 把 traceId 定义为跨服务关联键：上游存在则透传，链路起点则生成。
- 把“日志是否产生”和“日志是否能按 traceId 查询”分开说明。
- 让定时任务默认静默，仅在异常、阈值、状态变化或预先开启诊断时输出。
- 明确诊断必须在执行前开启；已被抑制的日志不能事后补回。
- 保留循环汇总、失败采样、Metrics、DEBUG 热开和异步上下文清理要求。

**Non-Goals:**

- 不实现具体语言的日志框架、动态配置中心或日志平台查询接口。
- 不改变 HTTP/MQ/RPC 的业务协议，只在示例中说明使用现有链路元数据传播机制。
- 不要求所有定时任务都持久化完整过程日志。

## Decisions

### 1. 使用“建立 trace context”替代“必须接收 traceId”

入口先校验并透传上游 trace context；没有上游时生成新的 traceId。这样 HTTP、MQ、RPC、定时任务都能满足业务日志关联要求，同时不会误导读者认为定时任务需要伪造入站 Header。替代方案是要求所有场景都接收 Header，但不适用于定时任务和独立批处理。

### 2. 定时任务采用“默认静默 + 条件输出”

成功且无诊断条件的普通执行不打印固定 INFO 开始/结束日志；失败、超时、重要状态变化、失败率阈值和人工诊断才输出。Metrics 负责高频数值，批次汇总和有限样本负责业务结果。替代方案是每次打印开始/结束并依靠采集端过滤，仍会产生无价值 I/O 和索引成本，因此不采用。

### 3. 诊断 traceId 必须在执行前确定

人工诊断可以通过管理入口、调度参数或受控配置预先指定 traceId/诊断范围；定时任务也可以在异常时使用本次执行已生成的 traceId。所有下游 HTTP/RPC 调用继续传播该 ID。不能承诺对已静默完成的执行事后补日志，因为日志事件本身没有发生。

### 4. 文档按“总原则—场景—速查—反模式”同步

`SKILL.md` 写总原则与五条铁律的边界；`scheduled-job.md` 写默认静默和诊断流程；`decision-matrix.md` 写级别/频次选择；`anti-patterns.md` 写固定成功日志、无 trace context 日志和事后补日志的反例。这样阅读、实施和 review 入口一致，避免只改场景文档造成冲突。

## Risks / Trade-offs

- [正常任务日志减少] → 用 Metrics、任务执行记录和失败/阈值日志保证结果可观测；明确事后不能补回过程日志。
- [诊断开关误配置导致刷屏] → 要求按任务/traceId 限定范围，配置访问控制、时间窗口、采样上限，并默认关闭。
- [跨服务传播丢失] → 将出站传播、异步上下文透传和 worker 清理列入场景 checklist；丢失时按 CRITICAL review。
- [traceId 格式与调度 executionId 混淆] → traceId 作为链路 ID，jobName/jobRunId 作为任务身份字段分开记录。

## Migration Plan

1. 更新 skill 总则、定时任务场景、决策矩阵和反模式清单。
2. 用 OpenSpec 严格校验并检查文档中的旧规则、示例和 checklist 是否互相矛盾。
3. 归档本次 OpenSpec；实际业务项目按新规则逐步调整定时任务日志，不要求本仓库提供运行时迁移脚本。
